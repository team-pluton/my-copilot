# 기술 구조와 SDK 경계

## SDK 확인 상태 — **여기가 이 문서의 핵심이다**

아래 표가 비어 있는 동안에는 어떤 코드도 "된다"고 전제하지 않는다.
확인한 항목만 날짜와 출처를 적는다.

| 모듈 | 쓰려는 곳 | 확인해야 할 것 | 상태 | 확인일·출처 |
|---|---|---|---|---|
| NaviHelper | 경유지 추가 | 메서드 존재·시그니처·콜백 | ☐ 미확인 | |
| NaviHelper | 경유지 슬롯 | 최대 개수 (2개라고 들음) | ☐ 미확인 | |
| NaviHelper | 현재 경로 | 목적지·남은 거리 조회 가능 여부 | ☐ 미확인 | |
| Vehicle/AAOS | 주행·정차 | 필요한 권한, 차량별 지원 | ☐ 미확인 | |
| Fused Location | 현재 위치 | 실제 제공 여부 ("준비 중" 표기가 있다고 들음) | ☐ 미확인 | |
| TTS | 음성 안내 | 차량 오디오 정책 | ☐ 미확인 | |
| 장소 API | 휴게소 검색 | 재배포·캐싱·차량용 사용 조건 | ☐ 미확인 | |

## 층 구조

```
UI         Kotlin · Jetpack Compose · ViewModel
           └ 주행/정차에 따라 화면을 바꾼다

Domain     core/  ← Android 의존 없음. 단위 테스트 대상
           RecommendationEngine · BreakScheduler · Model

Port       core/Ports.kt  ← 우리가 정한 인터페이스
           VehicleStateProvider · LocationProvider
           NavigationProvider · RestStopRepository

Adapter    Pleos*Provider (실제)  /  Mock*Provider (시연·테스트)
Data       Room · DataStore · 장소 데이터 캐시
```

**`core` 는 Android 를 모른다.** 추천 엔진이 이 앱의 차별화 그 자체인데 그게
Android 에 묶여 있으면 차량·에뮬레이터 없이는 한 줄도 검증할 수 없다. 떼어
두면 JVM 테스트로 규칙을 증명할 수 있고, 그 테스트가 곧 심사 자료가 된다.

**SDK 는 Port 뒤에 숨는다.** 접근이 늦어지거나 막혀도 앱이 멈추지 않고,
시그니처가 바뀌어도 고칠 곳이 어댑터 하나다.

> ⚠️ 시연에서 **Mock 과 실제 연동을 섞어 말하지 않는다.** 어느 쪽인지 화면과
> 발표에서 분명히 구분한다. 흐려지면 심사에서 가장 크게 잃는다.

## 예외 처리 — 완성도는 여기서 갈린다

| 상황 | 앱의 행동 |
|---|---|
| GPS 수신 실패 | 마지막 위치를 현재 위치처럼 쓰지 않는다. 갱신을 기다린다 |
| 내비 연결 실패 | 경유지 추가 불가를 알리고 **기존 경로는 건드리지 않는다** |
| 차량 정보 권한 없음 | 주행 상태를 `UNKNOWN` 으로 두고 **수동 타이머**로 전환 |
| 장소 검색 결과 없음 | 조건 완화를 제안하거나 추천을 보류 (빈 목록을 띄우지 않는다) |
| 주행 중 | 장소 목록의 상세 탐색을 제한 |
| 경유지 슬롯 부족 | 기존 경유지를 **지우지 않고** 교체 여부를 묻는다 |
| TTS 불가 | 조용한 기본 알림으로 대체 |
| 앱 재시작 | 진행 중이던 여행 상태를 복구 |
| 네트워크 중단 | 이미 받아 둔 정보만 쓴다 |

## 개인정보

여행 경로를 서버에 영구 보관하지 않는다. 위치 접근 목적을 명확히 알리고,
사용자가 기록을 지울 수 있게 한다. MVP 에는 계정·로그인이 없다.
