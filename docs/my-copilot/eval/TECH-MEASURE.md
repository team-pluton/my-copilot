# 기술적 측정 — 헤드리스 브라우저가 센 탭 수 (사람 평가가 아니다)

측정일 2026-10-27 · 도구: puppeteer-core + 설치된 Chrome, 두 제품 모두 `localhost:3008`, 새로 고침·저장값 비움 후 시작 · 셸 전체 보기 · 세로.
**"최단 경로를 아는 사람이 누르는 횟수"**다. 평가자가 찾는 데 쓰는 탭·시간·실수는 들어 있지 않다 — 그건 `RECORD.md` 의 사람 측정이다.
실패 없이 끝난 경로만 적는다. 스크립트는 scratchpad `taps.cjs`(저장소 밖).

## 공통 과제 1+2 · "충전이 필요한지 확인 → 가장 먼저 권하는 곳을 경유지로"

| 제품 | 탭 | 경로 | 판정이 처음 보이는 시점 | 경유지 추가 확인 |
|---|---|---|---|---|
| 쉼표 DRIVE `/demo` | **2** | [충전·휴식 후보 보기] → [경유지로 추가] | **0탭** — 첫 화면(상태)에 부족 판정 | 추가됨(김천휴게소 · 경유지에 있음) |
| MY CO-PILOT `/copilot` | **5** | [가족 이동] → [출발 준비 시작] → [에너지 보기] → [충전·휴식 후보 보기] → [경유지로 추가] | **2탭** — 출발 준비 뒤 홈 제안 "충전이 필요할 수 있어요" | 추가됨(김천휴게소 · 경유지에 있음) |

## 읽는 법

- 차이 3탭의 내용: **프로필 선택 1** + **출발 준비 시작 1** + **에너지 화면 경유 1**. 앞의 둘은 MY CO-PILOT 이 "누구와 가나"를 먼저 묻는 설계의 값이고, 쉼표 DRIVE 는 가족 시나리오가 기본값으로 들어 있어 묻지 않는다 — 같은 과제지만 출발점이 다르다(공정성 주의, PROTOCOL).
- 셋째 탭(홈 → 에너지 → 후보)은 설계 선택이다. 홈 제안 카드에서 바로 후보로 가는 버튼은 **없다**(홈 버튼: 왜 이 제안인가요 · 에너지 보기 · 이번에는 건너뛰기 · 맞추기). 줄일 수 있는 자리지만, "판정 → 선택지 → 후보" 순서를 일부러 둔 것이라 사람 평가 결과를 보고 정한다.
- 측정하지 않은 것: 과제 3(대기 길어지면) — 두 제품의 경로가 달라 스크립트가 "찾는 과정"을 대신할 수 없다. 사람 측정만.

## 다시 재려면

```
TMP_PUP=%TMPDIR%/pup node taps.cjs     # 개발 서버 3008 켜 둔 상태
```
출력 JSON 의 `taps` 가 성공한 탭 수, `success` 가 [경유지 추가됨, 판정 문구] 두 검사의 결과. 두 번째 검사는 마지막 화면 기준이라 MY CO-PILOT 은 후보 화면에서 false 가 정상(판정은 홈·에너지 화면에 있다).
