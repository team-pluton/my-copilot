# 사용성 비교 시험 설계 — 기존 방식 vs MY CO-PILOT (ARRIVE READY)

작성 2026-11-13 · 오너 지시 7(E32 보완 평가) · 같은 날 오너 검토 반영(과제 세트 균형 · 만차 알림 동일 · '확인 가능한 조건 충족도') · 실행 예정 11/27~12/2 · **결과가 나오기 전에는 "몇 % 줄었다"를 어디에도 쓰지 않는다.**

## 1. 무엇을 확인하나

질문 하나: **같은 과제를 할 때 운전자의 검색 · 비교 · 판단 · 반복 입력이 실제로 줄었나**(제품 원칙 01 · 04).
줄지 않았거나 선택이 나빠졌다면 그대로 보고한다 — 이 시험은 홍보 수치를 만들려는 것이 아니다.

## 2. 과제 (두 조건에 똑같이)

| 과제 | 내용 | 끝난 것으로 보는 시점 |
|---|---|---|
| T1 처음 결정 | "12:30 광화문 고객사 미팅 · 주차 후 방문까지 10분 여유. 약속에 맞출 수 있는 주차장으로 내비 경로를 시작하세요." | 내비가 그 주차장으로 안내를 시작한 순간 |
| T2 상황 변경 | 진행자가 두 조건 모두 **같은 문장**으로 알린다: "지금 안내 중인 주차장이 만차로 바뀌었습니다. 약속에 맞추려면 어떻게 하시겠어요?" — 같은 시점 · 같은 시연 값([시연]). 측정은 **이 문장을 다 말한 순간부터** | 새 경로 시작 또는 "유지"라고 답한 순간 |

정차 중에만 한다(주행 중 조작 시험이 아니다 — Safety Gate). 실차가 아니라 Pleos Connect Emulator · 같은 PC.

T2 에서 B 는 앱이 스스로 다시 판단해 알림을 띄울 수 있다 — 그 알림은 **기능 동작으로 따로 기록**하고(떴는지 · 진행자 문장보다 먼저였는지), 측정의 출발점은 두 조건 모두 진행자 문장으로 같게 둔다. 그래야 '상황을 알게 된 속도'와 '알게 된 뒤 해결하는 부담'이 섞이지 않는다.

## 3. 조건

| | 기존 방식(A) | MY CO-PILOT(B) |
|---|---|---|
| 쓰는 것 | 폰의 지도 앱(주차장 찾기) + 서울시 주차 정보 웹(실시간 대수) + 에뮬레이터 내비(목적지 입력) | 에뮬레이터의 MY CO-PILOT(업무 이동 → 목표 카드) + 같은 내비 |
| 데이터 | 같은 시각의 같은 공공 데이터 | 같음 |
| 출발 상태 | 내비에 광화문 고객사가 목적지로 들어 있음 | 같음 |

과제 세트는 둘 — **광화문 세트**와 **시청 세트**(방문지 · 약속 · 여유가 다르고, 각 세트 안에서는 두 조건이 같은 데이터). 같은 사람이 같은 세트를 두 번 하지 않는다.
방식(A/B) · 순서 · 세트가 한쪽으로 쏠리지 않게 넷씩 돌린다:

| 참가자 | 첫 번째 | 두 번째 |
|---|---|---|
| P1 · P5 | A · 광화문 | B · 시청 |
| P2 · P6 | B · 광화문 | A · 시청 |
| P3 · P7 | A · 시청 | B · 광화문 |
| P4 · P8 | B · 시청 | A · 광화문 |

결과 표에는 세트별로도 나눠 보여 준다 — 한 세트에서만 차이가 나면 앱이 아니라 방문지 난이도 탓일 수 있다.

## 4. 재는 것 (정의를 미리 고정)

| 지표 | 정의 | 재는 방법 |
|---|---|---|
| 앱 전환 수 | 화면 앞에 보이는 앱이 바뀐 횟수 | 화면 녹화 + `dumpsys activity` 로그 |
| 조작 수 | 탭 · 글자 입력(글자 수와 별도) · 스크롤 | 화면 녹화에서 셈(두 사람이 따로 세고 맞춰 봄) |
| 판단 시간 | 과제 제시 → 주차장을 정했다고 말한 때 | 녹화 시각 |
| 경로 시작 시간 | 과제 제시 → 내비 안내 시작 | `onRouteStarted` 로그 / 내비 화면 |
| 확인 가능한 조건 충족도 | 고른 주차장이 그 시각 데이터로 ① 운영 중 ② 빈자리 표시 ③ 방문지 800m 안 ④ 약속까지 여유(내비 시간 기준)를 만족하는가 — 0~4. **'방문 성공률'이 아니다** — 주차 뒤 실제 걷는 시간 · 도착 때 빈자리 · 실제 방문은 이 시험에서 확인하지 않는다 | 시험 뒤 같은 데이터로 채점(채점 기준은 엔진과 별도로 사람이 확인) |
| 실패 기록 | **내비 실행 실패**(경로를 시작하지 못함 · 다른 곳으로 시작) 와 **판단 오류**(조건을 어긴 주차장을 고름 · 고르지 못함)를 따로 센다. 실패한 시도는 시간 · 조작 수의 중앙값에서 빼고 따로 표에 둔다 | 녹화 · 로그 |
| 변경 후 부담(T2) | 다시 검색한 횟수 · 다시 입력한 글자 수 · 원래 경로를 잘못 지운 일 | 녹화 |
| 이해도 | "지금 무엇을 해야 하는지 바로 알았다"(1~5) · 한 줄 자유 응답 | 과제 직후 질문 |

자동 경로 변경 · 사용자 승인 없는 설정 변경은 **0건이어야 한다**(넘으면 결함으로 기록).

## 5. 참가자 · 규모

- 운전 경력 있는 5~8명(팀 밖 · 차량 앱 개발 경험 없는 사람 우선). 이름 · 연락처는 기록에 남기지 않고 P1~P8 로만.
- 적은 수라 **통계적 일반화를 주장하지 않는다** — 중앙값 · 범위 · 사람별 표를 그대로 낸다.

## 6. 결과를 쓰는 규칙

- 결과 표는 사람별 원값 + 중앙값 · 범위. 평균 개선율(%)은 쓰지 않는다.
- B 가 더 나빴던 지표 · 사람도 같은 표에 둔다.
- 발표 · 문서 문장 예: "8명 중 6명이 앱 전환 없이 경로를 시작했다(기존 방식 중앙값 4회)". 측정 전에는 "측정 예정"으로만.
- 에뮬레이터 · 정차 · 시연 만차라는 조건을 결과 옆에 늘 적는다.

## 7. 준비할 것

- [ ] 두 조건의 시작 상태를 같은 스크립트로 맞추기(gateprobe 로 내비 목적지 설정 · 앱 데이터 초기화)
- [ ] 화면 녹화(`adb screenrecord`) + 로그 수집 스크립트
- [ ] T2 진행자 문장(두 조건 같음) · B 는 같은 시점에 개발용 만차도 켜 둔다(앱 알림은 기능 기록용 — 둘 다 [시연])
- [ ] 시청 세트 데이터 확인(서울 시영 주차 · 반경 안 후보가 광화문 세트와 비슷한 수인지)
- [ ] 채점표 · 질문지(종이 한 장)
- [ ] 예비 시험 1명(팀원)으로 시간 · 절차 점검 — 이 결과는 본 결과에 넣지 않는다
