# One Journey. One Decision. — 조사·설계 (2026-11-04)

> **구현 전 조사·설계 문서다.** 앱 코드는 바꾸지 않았다. `copilot-v5`·`stable-2026-11-02`·쉼표 DRIVE v3.1 은 그대로다.
> 근거 표기: **[공식]** 제공사 문서·메타데이터를 직접 읽음 · **[AAR]** 실물 SDK 클래스 확인 · **[에뮬]** 에뮬레이터에서 실제로 봄 · **[보도]** 언론·보도자료 · **[일화]** 포럼 경험담 · **[미확인]** 찾지 못함.

## 1. 결론

1. **방향은 맞지만, 첫 MVP 는 쉼표 DRIVE 와 거의 같은 제품이다.** "충전 + 가족 휴식을 한 번에"는 이미 `src/lib/core/engine.ts` 의 판단이다. 새로운 것은 **실제 외부 데이터**이고, 지금 빠진 것도 그것이다 — `docs/data/rest-stops.csv` 11곳의 신뢰도가 **전부 UNKNOWN** 이다.
2. **세 데이터로는 부족하다.** 배터리·충전소 상태·내비만으로는 "가족 휴식"을 판단할 수 없다. 시설 출처가 있어야 해서 **네 번째로 한국도로공사 휴게소 API** 가 필요하다.
3. **전 차종 확장인 일정 + 주차는 지금 만들 수 없다.** 차 안에서 일정을 가져올 공식 경로를 못 찾았고, 전국 실시간 주차 API 도 못 찾았다. 일정 맞춤은 네이버 오토앱이 이미 말하고 있다[보도].
4. **1차 접수(11/15) 출품물은 바꾸지 말 것을 권한다.** 남은 11일에 제품을 바꾸면 검증된 출품물만 흔들린다. MVP 는 별도 브랜치에서 관문(7절)부터 통과시킨다.

설계에 바로 영향을 주는 네 가지:

- **경로 전체 좌표(폴리라인) API 는 찾지 못했다**[AAR 클래스 이름·문자열 검색]. "경로 주변 충전소" 계산을 일반화할 수 없다. MVP 는 경부선 휴게소처럼 **구간을 미리 고른 목록**으로 한다.
- `settingType: AUTO` 는 **내비가 스스로 충전 경유지를 넣을 수 있다**는 뜻으로 읽힌다(추정). 그러면 경유지 슬롯 2개와 충돌할 수 있다. 정책 1(지우지 않고 묻는다)대로 처리해야 한다.
- `requestTrip` 이 되면 후보마다 **내비 자신의 도착 잔량**을 받아, 우리 추정보다 앞에 둘 수 있다.
- `RequestWaypointInfo` 는 poiId·address·poiSubId 가 필수다. 충전소 API 의 충전소 ID 는 내비 POI ID 가 아니므로, **빈 poiId 로 경유지가 되는지** 확인해야 한다.

**`statUpdDt` 를 신선도로 쓰면 안 된다.** 이 값은 **상태가 바뀐 일시**다[공식]. 밤새 아무도 쓰지 않은 정상 충전기는 값이 오래됐어도 믿을 수 있고, 통신이 끊긴 충전기는 값이 오래됐어도 믿을 수 없다. 값만으로는 둘을 구별하지 못한다. 그래서 "상태가 오래된 충전기 = 신뢰도 낮음"은 틀릴 수 있다. 다음 셋을 따로 저장한다.

| 시각 | 뜻 |
|---|---|
| `fetchedAt` | 우리가 받은 시각 — 지금 값인가 |
| `changedAt`(statUpdDt) | 마지막 상태 변화 — 오래 고정돼 있는가 |
| `arrivalAt` | 도착 예정 시각 — 지금 상태가 그때까지 의미 있는가 |

신뢰도는 초기 가설이고, G1 측정으로 맞춘다.

| 조건 | 판단 | 화면 말 |
|---|---|---|
| 조회 실패 · 받은 지 오래됨 | 모름 | "지금 상태를 몰라요" |
| 통신 이상 · 미확인 코드 | 모름 | "상태 확인 불가" |
| 운영 중지 · 점검 · `note` 의 이용 불가 | 후보에서 뺌, 이유 표시 | "점검 중으로 표시" |
| 대기 + 도착까지 짧음 | 보통 | "조회 시각 기준 N대 대기" |
| 대기 + 도착까지 김 | 낮음 | "도착 때는 달라질 수 있어요" |

"빈 충전기가 있어요"라고 **단정하지 않는다**. 대수가 많은 곳이 유리하도록 충전소 단위로 본다.

**키를 APK 에 넣지 않는다.** 저장소·APK 를 심사 제출하므로 키가 노출된다. `zcode` 단위라 응답도 크다(추정). 프록시가 필요하고, 공개 배포 금지 조건이 있으므로 MVP 는 **노트북 프록시 + `adb reverse`** 로 한다. 네트워크가 끊기면 "기록값 · 시각"으로 표시한다(정책 4).

## 6. 설계

### 6-1. Data Integration Hub

앱을 모으는 층이 아니라 **출처를 잃지 않고 값을 정규화하는 층**이다.

```
공급자 어댑터                        정규화                     사용
Pleos Vehicle ─┐
Pleos Navi    ─┤                ┌ VehicleEnergy ┐
환경공단 충전 ─┼→ Fact<T> 저장 ─┼ RouteContext  ┼→ Decision Engine → Safety Gate → 내비
도로공사 휴게소┤                ├ Stop(충전+시설)┤      ↑                  ↑
사용자 입력   ─┘                └ Mission·일행  ┘   현재 engine·Planner   RouteHandoff 와 같은 확인
```

```ts
type Fact<T> = {
  value: T | null;
  source: { provider: string; license: string; attribution: string };
  fetchedAt: number;          // 우리가 받은 시각
  sourceTime: number | null;  // 원천 시각
  sourceTimeMeans: "CHANGED_AT" | "MEASURED_AT" | "PUBLISHED_AT" | "USER_ENTERED"; // 같은 '시각'이 아니다
  trust: "HIGH" | "MEDIUM" | "LOW" | "UNKNOWN";
  trustReason: string;        // 사용자에게 그대로 보여 줄 수 있는 말
  access: "OK" | "DENIED" | "NOT_CONNECTED" | "FAILED";
  mode: "LIVE" | "RECORDED" | "MOCK"; // 정책 4 — 화면에 늘 표시
};
```

규칙:

- 공급자는 교체 가능한 어댑터다. 판단 코드는 공급자 이름을 모른다.
- 값이 없음(`null`)과 실패(`FAILED`)와 권한 없음(`DENIED`)을 합치지 않는다.
- 저장 제한은 공급자별 속성이다(TMAP 24시간 등). 캐시는 그 안에서만 한다.
- `src/lib/core` 는 고치지 않는다. Hub 가 기존 `RestStop` 모양으로 넘기면 `rank()` 를 그대로 쓴다. 충전기 상태처럼 새로 필요한 값은 새 층(`src/lib/assistant/` ↔ `core/assistant/`, 거울 규칙)에 둔다.

### 6-2. Decision Engine — 나열이 아니라 결정 하나

| 단계 | 하는 일 | 재사용 |
|---|---|---|
| 1. 질문 정하기 | 지금 내려야 할 결정이 있는가. 없으면 말하지 않는다 | 플래너 집계 · Mission |
| 2. 배제 | 도달 불가(비관 추정) · 필수 시설 없음 · 커넥터 불일치 · 점검 중 | `excluded()` · 에너지 추정 |
| 3. 불확실성 처리 | 모르는 값을 0점으로 치지 않고 "모름"으로 남긴다 | `DataConfidence` 확장 |
| 4. 비교 | 에너지 여유 · 일행 조건 · 우회 · 신뢰도 | `rank()` · `breakdown()` |
| 5. 답 | 아래 네 가지 중 하나 | 신규 |
| 6. 실행 | 승인 → Gate → 경유지 → **콜백 + 재조회** | `gate` · `RouteHandoff` |
| 7. 재판단 | 판단을 뒤집을 사실이 바뀔 때만 다시 묻는다. 자동 변경 없음 | 누적 재판단 |

```ts
type Decision =
  | { kind: "NO_STOP_NEEDED"; why: Evidence[] }                         // "안 서도 된다"도 답이다
  | { kind: "GO_HERE"; stop: Stop; why: Evidence[]; alternative: Stop | null; flipIf: string[] }
  | { kind: "YOUR_CALL"; options: [Stop, Stop]; tradeoff: string }      // 정말 값어치가 갈릴 때만
  | { kind: "CANNOT_JUDGE"; missing: Fact<unknown>[]; doThis: string }; // 모르면 모른다고
```

`flipIf` 는 이 구조의 핵심이다. "이 충전소가 점검으로 바뀌면 다시 물을게요"처럼 판단을 뒤집는 조건을 함께 말한다. 주행 중에는 한 줄 + 음성만, 비교는 정차 중에만 한다(정책 7). 범위와 "추정" 표기, 우회 시간을 모르면 "추가 N분"을 쓰지 않는 규칙도 그대로다(정책 2).

### 6-3. 플랫폼 확장

Hub 와 Engine 은 도메인을 모른다. 결정 유형이 늘 때마다 **공급자 묶음 + 배제 규칙 + 비교 축**을 더한다.

| 결정 유형 | 공급자 | 언제 가능한가 |
|---|---|---|
| 어디서 충전하며 쉴까(EV) | 차량·내비·환경공단·도로공사 | **지금 시도 가능** |
| 안 서도 되나(EV) | 차량·내비 | 지금 |
| 방문 뒤 귀가까지 되나(공통) | 차량·내비·Mission | E23 위에 이어짐 |
| 언제 출발할까(공통) | 일정 수동 입력·내비 `TripInfo.eta` | 수동이면 가능. `requestTrip` 확인 후 |
| 어디 주차할까(공통) | 표준데이터 + 지역 실시간 | 잔여 면수 없는 지역이 많음 |
| 일정 자동 연동 | 폰 연동 경로 | 공식 경로 확인 후 |

## 7. EV 충전 + 휴식 vs 일정 + 주차 + 방문

| 기준 | EV 충전 + 휴식 | 일정 + 주차 + 방문 |
|---|---|---|
| 데이터 지금 확보 | 가능 (무료 공공) | 일정 경로 없음 · 주차 반기/지역 한정 |
| SDK 활용 | 깊음 — 배터리·`requestTrip`·경유지 | 얕음 — 내비 중심 |
| 대상 | Pleos EV 운전자 | 다양한 동력원 |
| 사용 빈도 | 낮음 (장거리 때) — 사업성 약점 | 높음 |
| 겹침 | 내비 충전 계획 · **쉼표 DRIVE** | 네이버 오토앱 · 지도 앱 |
| 실패 비용 | 큼 — 도착했는데 못 쓰면 일정 전체가 무너짐 | 작음 |
| 11/15·12/3 안 시연 | 가능 | 수동 입력·정적 데이터 수준 |

**권고:** EV 충전 + 휴식을 **첫 실증**으로 하자는 제안에 동의한다. 실패 비용이 큰 결정이라 "한 번에 끝낸다"의 가치도 가장 크다. 일정 + 주차는 **데이터 경로가 열릴 때까지 비전으로만** 말한다. 공통 기능 쪽의 지금 실체는 E23 의 "방문 뒤 귀가까지"다.

### 관문 — 구현 전에 순서대로

| # | 확인 | 방법 | 실패하면 |
|---|---|---|---|
| G1 | 경부선 휴게소 충전기 상태가 실제로 쓸 만한가 | 키 발급 → 72시간 수집: 조회 실패율 · 상태 변화 빈도 · 통신 이상 비율 · 몇 곳 현장 대조 | 상태를 빼고 설비 정보만 사용 |
| G2 | 경유지 콜백 · 빈 poiId | 에뮬레이터에서 경로 설정 뒤 `addWaypoint` (E11 재개) | 내비 검색 화면으로 넘기기 |
| G3 | 앱에서 외부 호출 | 에뮬레이터 + `adb reverse` | 기록값으로만 시연 |
| G4 | `requestTrip` 동작 · 단위 · `AUTO` 지점 | 에뮬레이터 | 우리 추정만 사용 |
| G5 | 기본 내비와 같은 조건 비교 | 서울→부산 설정 후 내비 화면 기록 | 차별 문구 수정 |

G1·G2 가 무너지면 MVP 의 핵심이 사라지므로 먼저 한다.

## 8. 세 데이터 + 하나로 시연하는 MVP

**범위:** 경부선 부산 방향 휴게소 11곳. 가족 서울→부산 시나리오(47% 부족 유지). 장소 검색·지도 없음.

| 데이터 | 등급 목표 | 쓰임 |
|---|---|---|
| Vehicle SOC · 용량 | 실제 SDK(에뮬) | 도달 가능 판단 |
| NaviHelper | 실제 SDK(에뮬) | 경로 · 도착 잔량(G4) · 경유지 실행 |
| 환경공단 상태 | 실제 API(프록시) / 끊기면 기록값 | 상태 · 대수 · 출력 |
| 도로공사 시설 | 실제 API 또는 확인일 표기 스냅숏 | 수유실 등 일행 조건 |

**화면 흐름(정차 중):**

1. 일행 선택(이미 있음) → 2. 경로 인식 → 3. 답 하나: "**OO휴게소에서 충전하며 쉬어 가세요**" + 근거 3줄(도착 잔량 범위 · 수유실 있음 · 급속 N대, 조회 시각) + 대안 하나 + "상태가 바뀌면 다시 물을게요" → 4. [경유지로 추가] → 5. 콜백·재조회 뒤 "내비가 확인함".

**시연의 핵심 장면:** 추천한 곳의 상태가 조회 시 점검으로 바뀐 경우를 **기록값으로 재현**해 대안으로 넘어가는 장면. 화면에 "기록값"을 표시한다.

**규모(추정):** 관문 통과 후 어댑터·Fact·Decision·거울 테스트·화면 한 장, 약 5~7일. 11곳 ↔ 충전소 ID 대조는 **수작업 검수**한다(방향 착오 전례: 죽암).

## 9. 측정 — 줄였다고 말하기 전에

지금 "세 앱을 한 번으로"는 **가설**이다. 근거는 해외 포럼 일화뿐이고([Rivian 포럼](https://www.rivianforums.com/forum/threads/abrp-4-5-0-gets-a-major-upgrade.17896/post-378484), [TidBITS](https://tidbits.com/2026/07/10/how-planning-made-my-second-long-ev-trip-stress-free/)), 국내 자료는 찾지 못했다. 원래 제안 글의 아이오닉 사례 링크는 원문을 확인하지 못했다.

**과제(정차 상태에서만):** "아이와 부산에 간다. SOC 47% 조건. 어디서 충전하고 쉴지 정해 내비에 넣어라."

| 비교군 | 구성 |
|---|---|
| A | 기본 내비 + Gleo AI 만 |
| B | 내비 + 폰의 충전 앱·지도 (평소 방식) |
| C | MY CO-PILOT |

| 지표 | 재는 법 |
|---|---|
| 앱 전환 횟수 | 화면 녹화에서 앱 전환 집계 |
| 조작 수 | 터치 로그·녹화 (최단 경로 수치와 구분 — `eval/TECH-MEASURE.md`) |
| 결정 시간 | 과제 시작 → 내비 경유지 확정 |
| 결정 실패 | 도달 불가 · 필수 시설 없음 · 점검 중 선택 · 포기 |
| 근거 이해 | "왜 거기인가" 설명 가능 여부 |
| 신뢰 · 재사용 | 사후 질문 |

**데이터 품질은 따로 잰다:** 상태 정확도(현장 대조) · 조회 실패율 · `CANNOT_JUDGE` 비율.

**기록 원칙:** 평가자 수를 그대로 쓴다. 3~5명이면 경향으로만 말하고 통계처럼 쓰지 않는다. 사람을 안 만났으면 "미측정"이라 쓴다. 절차는 `docs/my-copilot/eval/` 을 확장한다. **주행 중 측정은 하지 않는다.**

## 10. 공모전에서의 위치

| 심사 기준 | 말할 수 있는 것 | 조건 |
|---|---|---|
| 차량특화성 | 내 차 배터리 + 내비 경로 + 승인 후 경유지 + 주행 중 한 줄. 폰 앱만으로는 차량 신호와 내비 실행까지 잇기 어렵다 | G2 |
| 창의성 | 충전소 추천이 아니라 **일행 조건·신뢰도까지 합친 결정 하나, 판단이 뒤집힐 조건 공개** | G5 |
| 기술 활용성 | Vehicle + NaviHelper 깊은 사용 + 콜백 검증(E23) | 달성 일부 |
| 사업성 | 공급자 추가형 플랫폼 · 다른 동력원은 귀가·출발 판단부터 | 수치는 "목표"로만 |

**말하지 않을 것:** "빈 충전기 보장" · "전 차종 지원" · "현대차에 없는 기능" · "앱 전환 N% 감소"(측정 전) · 연동하지 않은 공급자를 연동한 것처럼.

**출품과의 관계:** 1차 출품은 쉼표 DRIVE v3.1 이다(오너 결정 2026-10-26). "One Decision"은 사실상 **쉼표 DRIVE 판단에 실제 데이터를 붙인 다음 단계**다. 따로 내세우면 자기 출품작과 경쟁하게 된다. 요강상 PT 이후 추가 개발은 순위에 반영되지 않는다고만 돼 있어, PT 전 개선의 반영 범위는 2차 기준 안내로 확인해야 한다. 서류 통과 후 PT 판에 실데이터를 올릴지 결정하는 길이 가장 현실적이다.

## 11. 오너 결정이 필요한 것

1. **MVP 를 어디에 붙이나** — 권고: 지금은 실험 브랜치, 서류 통과(11/23) 후 쉼표 DRIVE PT 판 반영 여부 결정.
2. **공공데이터 키 신청** — 오너 계정으로 환경공단·도로공사 활용 신청. 키는 저장소에 넣지 않는다.
3. **G1·G2 착수 승인.** 코드 변경은 측정 스크립트와 에뮬레이터 확인뿐이다.
