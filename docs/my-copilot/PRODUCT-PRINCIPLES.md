# MY CO-PILOT — CORE PRODUCT PRINCIPLES (최상위 제품 개발 정책)

> **오너 결정 2026-11-11.** 이 문서가 모든 제품·기능·UX 판단의 **가장 위**에 있다. V7 비전(`v7/PRODUCT-VISION-V7.md`)·V6 엔진·화면 정책은 이 원칙 아래에서 해석한다.
> 배경: 세 차례 화면 수정으로 차량 제어·상태 확인·안전성은 정리됐지만, 외부 서비스 정보를 판단에 쓰는 통합 사례가 **EV 충전 하나뿐**이었다(비EV 0). 화면 다듬기가 핵심 기능 개발을 늦추지 않게 기준을 고정한다.
> **목표: 대상 수상 — 단, 실제 구현·측정·검증된 차별성으로 경쟁한다.** 심사위원이 "현대차에 이런 앱이 실제로 탑재되면 쓰겠다"고 느낄 독립적인 존재 이유.

## 1. 존재 이유

**여러 앱을 오가던 운전자의 일을, 하나의 지능형 이동 경험으로.**

MY CO-PILOT 은 차량용 앱의 기능을 모아 놓은 런처가 아니다. 운전자가 내비게이션 · 차량 설정 · 충전 · 주차 · 일정 · 장소 정보를 각각 확인하고 비교하며 직접 조작해야 하는 불편을 줄이려고 만든다.
목적은 앱을 많이 연결했다는 사실이 아니라, **여러 서비스의 정보를 하나의 이동 판단으로 결합해 사용자가 해야 할 일을 실제로 줄이는 것**이다.

## 2. 절대 유지할 여섯 가지 철학

| # | 원칙 | 뜻 |
|---|---|---|
| 01 | **Multi-Service Integration** | 여러 앱·서비스의 정보를 **실제로** 연결한다 |
| 02 | **Context-Aware Intelligence** | 운전자 · 동승자 · 차량 상태 · 이동 목적과 일정에 맞춰 판단한다 |
| 03 | **Goal-Oriented Assistance** | 목적지 도착이 아니라 사용자가 하려는 **실제 일**을 중심으로 돕는다 |
| 04 | **Minimum Driver Effort** | 검색 · 앱 전환 · 비교 · 입력을 최소화한다 |
| 05 | **One Decision, Verified Execution** | 필요한 선택 하나를 제안하고, 승인된 행동을 실행한 뒤 결과를 확인한다 |
| 06 | **Trust & Driving Safety** | 확인되지 않은 정보는 단정하지 않고, 주행 안전과 운전자 통제권을 지킨다 |

**01 과 04 가 MY CO-PILOT 이 존재하는 이유다.** 신규 기능과 UX 변경은 이 여섯 가지 중 어디에 기여하는지 설명할 수 있어야 한다.

## 3. 제품 구조 — Journey OS

| 계층 | 역할 | 지금 코드 |
|---|---|---|
| Journey Goal Engine | 사용자의 실제 이동 목표 관리 | V5 Mission(픽업·귀가) · `JOURNEY-GOAL-SPEC.md` [설계] |
| Context Engine | 차량 · 운전자 · 동승자 · 이동 상태 | `assistant/` situation · journey · cabin |
| Service Integration Layer | 내비 · 충전 · 주차 · 일정 등 연결 가능한 서비스 | NaviHelper · 충전소 프록시 [실 API] · 주차 [실 API 관문만] · 일정 [없음] |
| Decision Engine | 필수조건 검증 · 후보 비교 · 추천 | V6 IntegratedDecision |
| Action & Verification Layer | 승인 · 실행 · 결과 재조회 | WaypointHandoff · RouteHandoff · Cabin settle |
| Safety & Trust Layer | 주행 제한 · 권한 · 최신성 · 오류 | SafetyGate · JourneyFact 신선도 |

EV 에너지 판단과 공조·시트 개인화는 이 플랫폼 아래의 **전문 모듈**이다.

## 4. 주력 사용자 경험 — 사용자가 해결하려는 일 (탭·별도 앱으로 나누지 않는다)

| 순위 | 경험 | 해결하는 일 | 상태 (2026-11-11) |
|---|---|---|---|
| 1 | **ARRIVE READY** — 약속에 맞춰 방문하기 | 일정 · 목적지 · 이동 시간 · 주차 정보를 연결해 실제로 방문할 수 있는 계획 | **[미구현]** · 관문 A·B·C 통과(주차 [실 API] · ETA·경로 [에뮬]) · 일정 제공자 없음 → 사용자 입력 |
| 2 | **JOURNEY RECOVERY** — 계획이 틀어졌을 때 복구 | 외부 조건이 바뀌면 다시 여러 앱을 열지 않고 대안 | 충전소 상태 · 배터리 변화 재판단 [에뮬] · 주차·교통 변화 [미구현] |
| 3 | **FAMILY JOURNEY** — 가족 이동을 끊김 없이 | 픽업 · 대기 · 귀가를 하나의 Mission 으로, 동승자·차량 상태에 맞춰 준비 | 구현 [에뮬 E28] · 외부 일정·교통 연동 [미구현] |
| 4 | **ENERGY & STOP** — 충전과 휴식을 하나로 | EV 에너지 + 실제 충전소 상태 + 동승자 조건 → 이동 가능한 경유지 | V6 [실 API]·[에뮬] · 전체 실데이터 범위는 휴게소 매핑 8곳까지 |

네 경험은 **하나의 Journey Goal Engine** 이 이동 목적에 따라 필요한 서비스를 골라 결합하는 구조로 만든다. 가장 큰 차별화 기회는 **ARRIVE READY → JOURNEY RECOVERY 연결**이다 — 출발 알림이 아니라, 이동 중 계획이 틀어졌을 때 주차 앱을 다시 열고 목적지를 다시 입력하는 과정을 없애는 것.

## 5. 반드시 막을 실패

- 기능만 많은 **차량 설정 앱**이 되는 것
- **EV 충전 추천 앱**으로 정체성이 줄어드는 것
- 단순 **앱 런처**나 통합 정보 **대시보드**가 되는 것
- 상황마다 운전자에게 **입력을 반복** 요구하는 것
- 여러 추천 카드와 버튼을 **동시에** 노출하는 것
- 외부 API **조회 성공**을 통합 의사결정 **성공으로 과장**하는 것
- 데이터나 권한이 없는데 **실행됐다고 표시**하는 것
- 지원되지 않는 앱 간 연동을 **이미 가능한 것처럼** 주장하는 것
- 근거 없이 **전 차종 지원**을 확정하는 것
- **UI 수정 때문에 핵심 기능 개발이 계속 늦어지는 것**

## 6. 기능 평가 기준 (모든 신규 기능)

| 기준 | 확인할 것 |
|---|---|
| 앱 통합 가치 | 분리돼 있던 서비스 **두 개 이상**의 정보를 실제로 결합하는가 |
| 사용자 편의 | 다른 앱으로 가거나 직접 비교하는 일을 줄이는가 |
| 상황 판단 | 이동 목적·차량·운전자 상황에 따라 결과가 달라지는가 |
| 실행 가능성 | 승인된 행동을 실제 지원되는 차량·내비 기능으로 잇는가 |
| 신뢰성 | 외부 데이터 오류 · 최신성 · 권한 부족을 안전하게 다루는가 |
| 반복 이용성 | 한 번의 이벤트가 아니라 일상에서 다시 쓸 이유가 있는가 |
| 차량 특화성 | 스마트폰 앱보다 차량에서 줄 가치가 있는가 |

**핵심 상품 경험**은 앞의 두 기준(통합 가치 · 사용자 편의)을 반드시 충족한다. 공조 제어 · 기록 · 안전 확인 같은 **보조 기능**은 외부 앱 두 개를 잇지 않아도 핵심 경험을 받치는 역할로 유지할 수 있다.

## 7. 신규 기능 승인 문서 (A~J)

| | 질문 |
|---|---|
| A | 사용자가 원래 해야 했던 일 |
| B | 지금 몇 개의 서비스·앱을 오가야 하나 |
| C | MY CO-PILOT 이 실제로 가져오는 데이터와 공급자 |
| D | 서로 다른 데이터를 결합해 어떤 판단을 하나 |
| E | 판단 결과에 따라 어떤 행동이 달라지나 |
| F | 사용자가 해야 하는 조작 |
| G | 승인 후 실제로 실행하고 확인할 수 있나 |
| H | 실패하거나 정보가 부족하면 어떻게 하나 |
| I | EV 가 아닌 차량에서도 유효한가 |
| J | 반복 이용할 이유 |

**핵심 기능은 A~H 에 구체적인 답이 있어야 한다.** 정보 표시만 더하는 기능은 핵심 상품으로 올리지 않는다. (첫 적용: `v7/ARRIVE-READY-BUILD-PLAN.md`)

## 8. 서비스 실증 기준 — "통합 완료"라고 말하려면

- 서로 다른 서비스의 **실제 데이터**가 확인된 범위에서 수신된다
- 데이터마다 **출처 · 시각 · 정확도 · 권한 상태**를 추적한다(V6 `FactMeta`)
- **둘 이상의 데이터가 실제 추천 결과나 행동 결정에 영향**을 준다
- 같은 조건에서 기존 방식과 **사용자 조작 부담을 비교**할 수 있다(Gate E)
- 승인 없이 내비 경로·차량 설정을 **바꾸지 않는다**
- 실행 결과를 **콜백·재조회**로 확인한다
- 미확인은 **미확인**으로 표시한다

## 9. 개발 우선순위 (2026-11-11 확정)

| 순서 | 목표 | 성공 기준 |
|---|---|---|
| P0 | 1차 제출본 안정화(11/15) | 필수 서류 · APK · 영상 · 익명성 검증 완료 — **검증된 V6 코드를 보호**, V7 은 비전·실증 로드맵으로 전달 |
| P1 | ARRIVE READY 데이터 연결 관문 | 실제 주차 정보 + 쓸 수 있는 ETA·경로 정보 확보(A·B·C 통과 — D·E 남음) |
| P2 | 공통 Journey Goal Engine | 이동 목표 · 제약 · 서비스 데이터 · 실행 결과 통합 |
| P3 | 비EV 통합 시나리오 완성 | 일정(입력) · 주차 · 내비를 실제로 결합한 판단 → 승인 → 실행 |
| P4 | JOURNEY RECOVERY | 조건 변경 시 근거 있는 대안 재계산 |
| P5 | 사용성 검증 | 앱 전환 · 입력·터치 수 · 판단 시간 비교 |

**2차 본선(12/3~4)의 최우선 목표 = 실제로 작동하는 비EV 외부 서비스 통합 장면.** 기능별 탭·설정 메뉴 추가는 최소화한다. 기존 EV 엔진·개인화·Mission 은 재사용한다.

## 10. 변경 통제 — Claude 가 먼저 보고할 세 가지

기능을 더하거나 고치기 **전에**:

1. 이 변경이 **여섯 가지 철학** 중 어디에 기여하나
2. 사용자가 원래 해야 했던 **어떤 일이 사라지나**
3. **검증된 기능·출품 일정**에 어떤 영향을 주나

셋이 설명되지 않는 기능 추가는 우선순위를 올리지 않는다.

## 11. 화면·리뷰를 볼 때의 순서

① 핵심 철학이 살아 있나(서비스를 실제로 잇나) → ② 운전자의 일이 실제로 줄었나(앱 전환 · 검색 · 비교 · 터치 · 반복 입력) → ③ 현대차 기본 기능(Gleo AI · 기본 내비)과 구분되나 → 그다음 UI · 안전성 · 안정성 · 구현 가능성.

## 12. 성공 기준

운전자가 여러 앱을 켜고 찾아 비교하던 일을 MY CO-PILOT 이 대신하고, 사용자는 필요한 순간에 **최소한의 선택**만으로 이동 목표를 이룬다. 차량 환경에 맞게 안전하고, 검증 가능하며, 반복해서 쓸 가치가 있어야 한다.
