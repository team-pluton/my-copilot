# NaviHelper 연동 — 무엇이 실제로 되나

프로젝트 AAR: NaviHelper **3.0.5** + navi-data **3.0.4** · 에뮬레이터 서비스 3.0.4 · 내비 Navi42 3.3.2. 공식 문서는 v3.0.5 기준이고 쓴 API 는 실행까지 일치했다.

| 기능 | API | 결과 (에뮬레이터 2026-11-04) |
|---|---|---|
| 현재 목적지 | `getDestinationInfo` | ✅ 이름·좌표 |
| 경유지 목록 | `getWaypointInfo` | ✅ 단, **이름만 있고 좌표가 (0, 0)** |
| 경유지 추가 | `addWaypoint` | ✅ 내비 경로에 반영 · 빈 poiId 로도 됨 · 내비가 앞으로 나온다 |
| 칸 교체 | `removeWaypoint` → `addWaypoint` | ✅ 고른 칸만 교체, 다른 칸·목적지 유지 |
| 추가 콜백 | `onWaypointChanged` | ⚠️ 왔을 때도(12초 뒤), 안 왔을 때도 있음 |
| **후보까지 계산** | `requestTrip` | ✅ 거리·시간·도착 잔량. 경로 안 바뀜 |
| 도착 잔량 | `RouteStateInfo.remainDestinationChargingInt` | ⚠️ 75,580 — **%가 아니라 Wh 로 보임**(÷77,400 = 97.6%, 내비 화면 98%) |
| 경로 여부 | `RouteStateInfo.isRouting` | ❌ **안내 중에도 false** — 믿으면 안 된다 |
| 경로 좌표 | — | 없음(클래스 검색). 별도 공급자 미확보 |
| 주행 중 변경 제한 | SDK 강제 여부 미확인 | 앱이 정차 중에만 버튼을 낸다 |

`requestTrip` 실측: `distance=192949`(m) · `eta=9421`(초) · `socAtDest=64`(%) · `energy=27436`(Wh 추정). 내비 화면의 192km · 64% 와 일치한다. 첫 시도는 인자 순서를 틀려 230km · 57% 를 받았다. `TripRequest` 는 `(lat, lon, poiId, poiName, poiSubId)` 순서다.

**아직 판단에 넣지 않았다.** 단위 확인이 1회뿐이고 한 후보씩 비동기로 불러야 한다. 넣으면 "경로 km 는 수기 목록"이라는 약점과 우회 판단이 크게 나아진다 — 다음 작업 1순위 후보.

## 실제 실행에서 나온 결함과 수정

| 현상 | 원인 | 수정 |
|---|---|---|
| 안내 중인데 "목적지가 없어요" | `isRouting` false | 목적지 재조회까지 함께 본다 |
| V5 "집으로 안내 시작"이 기존 경로를 확인 없이 덮을 수 있음 | 같은 값 사용 | `PleosNaviRoute` 도 목적지 기준으로 수정. **이 브랜치에서만** — `copilot-v5` 에는 그대로 있고, 교체 확인 실행은 미검증 |
| 들어갔는데 "찾지 못했어요" | 목록 좌표 (0, 0) | `sameWaypoint`: 좌표가 비면 이름 비교 |
| 응답 없으면 곧바로 실패 → 중복 추가 위험 | 빈 목록을 실패로 판정 | 콜백 없으면 '모름' 유지, 5초마다 12번 재조회, 그 뒤 "확인하지 못했어요" |
| 앱이 뒤에 있으면 응답 지연 | 내비가 앞으로 나옴 | 앱이 앞으로 오면 다시 읽는다 |

## 지키는 규칙

승인 전 변경 없음 · 경로 없으면 보내지 않음 · 칸이 차면 고르게 함 · 목록 재조회로만 "추가됨" · 응답 없으면 재전송 안 함 · 이미 있으면 보내지 않음.

## 미확인

`ADD` 콜백이 안 오는 조건 · 실차 · App Market 권한 · 주행 중 동작 · `isRouting` 이 true 가 되는 때.
